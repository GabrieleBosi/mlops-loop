What "agentic" actually means

An agentic workflow uses an LLM to carry out some or all of the steps in a multi-step task — drafting, checking, calling tools, revising — instead of producing one answer in a single pass. It's the difference between typing an essay start-to-finish with no backspace and writing the way a person does: outline, draft, research a gap, revise.

"Agentic" is a spectrum, not a binary. Arguing over whether something is "a true agent" is wasted energy; the useful question is how much autonomy the task needs. More autonomy means more flexibility — and less predictability, harder debugging, harder evals.

Level 1

Single call

One prompt, one answer. No agency — your baseline to beat.

Level 2

Fixed workflow

You hard-code the step sequence; the LLM executes individual steps. Predictable, testable.

Level 3

Model picks the path

The LLM decides which tool or branch to use next, within bounds you set.

Level 4

Model plans the steps

The LLM decomposes the goal itself and loops until done. Powerful, least predictable.

More predictableMore autonomous
Rule of thumb

Choose the lowest level of autonomy that passes your evals. Most business workflows that look "agentic" ship as Level 2–3. Reserve Level 4 for tasks where the steps genuinely can't be known in advance.

Why bother? Iteration compounds quality: a mid-tier model wrapped in a good agentic loop can outperform a frontier model prompted zero-shot — a result Ng has shown repeatedly on coding benchmarks. The workflow design, not the model choice, is usually the bigger lever. It also unlocks tasks a single call simply cannot do: anything requiring live data, actions in external systems, or work that exceeds one context window.

Step 02

Decompose the task before you touch a framework

Every agentic system starts the same way: watch how a skilled human does the job, and write down the steps.

  • List the human steps. Concrete verbs, in order. "Read the invoice → check it against the PO → flag mismatches → draft the reply."
  • Assign an executor to each step: an LLM prompt, deterministic code, a tool call (API, database, search), retrieval, or a human checkpoint. Not everything should be an LLM call — code is free, exact, and testable.
  • Name each step's input and output. Explicit interfaces are what make component-level evals possible later.
  • Mark the risky steps. Where would a human double-check their work? Those steps are your first candidates for reflection and evals.

Worked example — "answer an inbound RFP"

Retrieve product docsTool (search / RAG)Requirements → relevant doc chunks

Once the table exists, the architecture is nearly decided: each row becomes a component, risky rows get the reflection pattern, tool rows get the tool-use pattern, and the whole thing starts as a Level-2 fixed workflow — upgrade autonomy only if evals demand it.

Step 03

The four design patterns

Build each from first principles before reaching for a framework — the course does, and it's the fastest way to understand what any framework is doing for you. Patterns compose: most real systems use two or three.

  • Output quality matters more than latency, and you can afford 2–3× the tokens.
  • The output is checkable — code that runs, SQL that executes, JSON that validates, charts that render, claims with sources.
  • First-pass quality is inconsistent but the model can recognize its own errors when asked to look.

Typical wins from the course: chart-generation and SQL-generation workflows, where a reflection pass measurably lifts accuracy over direct generation.

A second LLM pass (often a different prompt playing "reviewer") critiques the draft against the task; a third pass revises. One to two rounds captures most of the gain — returns diminish fast after that.

The big lever is external feedback. Pure self-critique recycles the model's own beliefs. Feeding in objective signals — unit test results, a linter, the SQL error message, the rendered image — gives the critic new information and dramatically improves the loop. Prefer generate → run it → critique with results → revise whenever the output is executable.

reflection.py
def reflect_loop(task, max_rounds=2):
    draft = llm(f"Complete this task:\n{task}")
    for _ in range(max_rounds):
        checks = run_checks(draft)   # external signal: tests, linter, SQL EXPLAIN
        critique = llm(
            "You are a strict reviewer. Critique the draft against the task "
            "and the check results. List concrete problems. "
            f"Reply APPROVED if there are none.\n\nTask: {task}\n"
            f"Draft: {draft}\nCheck results: {checks}"
        )
        if "APPROVED" in critique:
            break
        draft = llm(
            f"Revise the draft to fix every problem listed.\n"
            f"Task: {task}\nDraft: {draft}\nProblems: {critique}"
        )
    return draft
  • A vague critic ("make it better") produces vague revisions — give the reviewer a rubric or checklist.
  • Self-critique with no new information can confidently approve wrong answers; add an external check wherever one exists.
  • Unbounded loops burn money — cap rounds, and stop early on APPROVED.
  • Don't reflect on everything. Apply it to the steps your error analysis flags, not the whole pipeline.
  • The task needs information the model doesn't have — live data, private systems, precise math.
  • The task needs actions, not just text: send, book, update, query.
  • You want deterministic sub-steps (calculations, lookups) done exactly rather than approximated in prose.

You describe functions to the model (name, description, typed parameters). The model doesn't execute anything — it replies with a structured request; your code executes it and feeds the result back, looping until the model answers.

The description is the interface. Write it for the model, not for humans: what the tool does, when to use it, when not to, and what the arguments mean. Most tool-selection failures are documentation failures.

Two force multipliers: code execution — a sandboxed interpreter is the universal tool for math, data wrangling and file work, and often replaces a dozen bespoke tools; and MCP (Model Context Protocol) — an open standard that lets you plug in servers exposing tools and data instead of hand-wiring every integration, so the ecosystem's connectors become yours.

tool_loop.py
TOOLS = [{
    "name": "get_invoice",
    "description": (
        "Look up one invoice by its exact ID. Use when the user references "
        "a specific invoice number. NOT for date ranges or totals."
    ),
    "parameters": {"invoice_id": "string"},
}]

def agent(user_msg, max_turns=8):
    messages = [{"role": "user", "content": user_msg}]
    for _ in range(max_turns):
        reply = llm(messages, tools=TOOLS)     # model answers or requests a tool
        if not reply.tool_call:
            return reply.text
        result = execute(reply.tool_call)      # your code runs it — sandboxed, validated
        messages += [reply, tool_result(result)]  # errors go back too; let it retry
    return "Stopped: turn limit reached."
  • Many overlapping tools confuse selection — fewer, sharper tools with when-NOT-to-use guidance beat a long menu.
  • Swallowing tool errors strands the model; return the error message so it can self-correct.
  • Side-effectful tools (send, delete, pay) need confirmation gates or human approval — design the blast radius, not just the happy path.
  • Sandbox code execution. Always.
  • The right sequence of steps varies per request and can't be hard-coded — open-ended research, "do whatever's needed" support tickets, ad-hoc analysis.
  • The action space is well-defined (a tool catalog) even though the ordering isn't.
Default the other way

If you can write the workflow as a fixed sequence, do — it's cheaper, faster, testable, and debuggable. Planning is the escalation, not the starting point.

Ask the model to produce an explicit plan — an ordered list of actions drawn from your catalog, with inputs — then execute steps one by one, feeding results into a shared state. When a step fails or reality diverges, re-plan from current state rather than pushing on.

A powerful variant from the course: planning with code execution — the model writes the plan as a program that calls your tool functions, and you run it. Loops, conditionals and data handling come free from the language instead of fragile prompt logic.

plan_execute.py
def plan_and_execute(goal, max_replans=2):
    plan = llm(
        f"Goal: {goal}\nAvailable actions: {ACTION_CATALOG}\n"
        "Write a numbered plan. One action per step, with its inputs."
    )
    state = {"goal": goal, "done": []}
    for step in parse(plan):
        result = execute(step, state)
        state["done"].append((step, result))
        if failed(result) and max_replans:     # reality drifted — re-plan, don't push on
            max_replans -= 1
            plan = llm(
                f"Step failed: {result}\nState so far: {state}\n"
                "Revise the remaining plan from here."
            )
    return state
  • Validate every planned step against the allowed action catalog before executing — models invent actions.
  • Cap iterations and re-plans; runaway loops are the signature failure of autonomous agents.
  • Plans go stale: execute against current state, and re-plan on surprise rather than trusting step 6 written before step 2 ran.
  • Log the plan itself — it's your best debugging artifact when things go sideways.
  • Subtasks need genuinely different contexts, instructions, or tool sets — a researcher, an analyst, a writer — and one mega-prompt is getting muddy.
  • Subtasks are independent enough to run in parallel.
  • You want a reviewer role that's structurally separate from the producer (reflection, scaled up).

Each "agent" is just an LLM configuration — a role prompt, a tool set, its own slice of context. The engineering is in how they communicate. The course's three core patterns:

  • Pipeline — sequential handoffs, each agent transforms and passes on. Simplest; errors compound forward.
  • Manager–workers — a coordinator decomposes the task, dispatches workers (in parallel where possible), synthesizes results. The workhorse pattern.
  • Peer collaboration — agents share a thread and debate or critique each other. Highest quality ceiling, highest cost and least predictable.
manager_workers.py
WORKERS = {
    "researcher": "You gather facts using the search tool. Return sourced notes.",
    "analyst":    "You turn research notes into three insights, with evidence.",
    "writer":     "You draft a one-page brief from the insights. Plain language.",
}

def run_team(task):
    assignments = llm(
        f"Task: {task}\nWorkers: {list(WORKERS)}\n"
        "Assign each worker one subtask. Reply as JSON."
    )
    outputs = {}
    for name, subtask in parse(assignments).items():   # parallelize when independent
        outputs[name] = llm(WORKERS[name] + "\n\nSubtask: " + subtask,
                            tools=TOOLS_FOR[name])
    return llm(
        f"Task: {task}\nWorker outputs: {outputs}\n"
        "Synthesize the final answer. Flag any disagreements."
    )
  • Start with the fewest agents that work — often one. Every handoff adds coordination cost and a new place for errors to compound.
  • Give each agent only the context it needs; forwarding everything to everyone recreates the mega-prompt you were escaping.
  • Eval the handoffs, not just the final output — inter-agent messages are where multi-agent systems quietly fail.
Step 04

The build loop: evals are the product

The course's sharpest lesson isn't a pattern — it's a process. Teams that ship agentic systems fast aren't better prompters; they're disciplined about this loop.

Build a quick end-to-end skeleton

Resist polishing components in isolation. A rough working pipeline — even one that's wrong half the time — reveals where the real problems are, and they're rarely where you guessed. Days, not weeks.

Read your traces

Log every step's input and output, then actually read them. Most insight in agentic development comes from eyeballing a handful of real traces, not from dashboards. If you can't see intermediate outputs, you can't debug the system — instrument first.

Run error analysis on failures

Take a sample of bad outputs, and for each one mark the first component where things went wrong. Tally the counts. The table — not intuition, not the newest technique on your feed — tells you where to invest. (Worked method in the next section.)

Build evals where the errors are

Start with ~20 examples from real inputs; grow the set every time you find a new failure. Two kinds, use both:

  • Objective, code-graded — wherever output is checkable: exact match, contains-the-fact, JSON validates, SQL returns the right rows, tests pass. Cheap, fast, trustworthy.
  • LLM-as-judge with a rubric — for subjective quality (tone, completeness, reasoning). Give the judge specific criteria, not "rate 1–10", and spot-check its verdicts against your own until you trust it.

Add component-level evals for the steps error analysis flagged — testing the retrieval step or the query-writer in isolation localizes regressions instantly.

evals.py
EVALS = load_jsonl("evals.jsonl")   # ~20 real examples to start; grows with every bug

def run_evals():
    rows = []
    for ex in EVALS:
        out = workflow(ex["input"])
        if ex["kind"] == "objective":
            score = check(out, ex["expected"])        # graded by code
        else:
            score = judge(out, rubric=ex["rubric"])   # graded by LLM + rubric
        rows.append({"id": ex["id"], "score": score})
    report(rows)   # per-example AND aggregate — read the failures, not just the number

Fix the weakest component, re-run, repeat

Work down this menu, cheapest first:

  • Sharpen the step's prompt; add 2–3 concrete examples of good output.
  • Split one overloaded step into two smaller ones.
  • Add external feedback or a reflection pass to that step.
  • Add, fix, or better-document a tool.
  • Swap the model for that step (bigger for hard steps, smaller for easy ones).
  • Fine-tune — last resort, after the workflow itself is right.

Your eval set doubles as a regression suite: every change gets re-scored, so you improve with confidence instead of whack-a-mole.

Step 05

Error analysis, the concrete method

Ten minutes with a spreadsheet beats a week of guessing. Here's the drill for a research agent with four components.

  • Collect 15–30 traces where the final output was wrong or weak.
  • For each, read step-by-step and mark the first component whose output went bad (blame upstream, not the messenger).
  • Tally per component. Fix the biggest count with the cheapest fix. Re-run evals. Repeat.

Headroom trick

Not sure a component is worth fixing? Replace its output with a hand-written perfect version for a few examples and re-run the pipeline. The end-to-end improvement is that component's headroom — invest where headroom is large, skip where perfection barely moves the needle.

This is also how you should evaluate hype: when a new technique or framework appears, ask which cell of your error table it improves. If the answer is "none", it's not for this project.

Step 06

Latency & cost — optimize last, measure first

Get quality right before speed: premature optimization hides quality problems and locks in the wrong architecture. When it's time, act on measurements, not vibes.

  • Profile per step. Trace latency and token spend for every component; fix the tallest bar. It's usually one or two steps, not "the model".
  • Parallelize independent steps. Fan out worker calls, retrievals, and per-section drafts concurrently — often the single biggest latency win.
  • Right-size models per step. Classification and extraction steps rarely need your best model; route easy steps to fast, cheap ones. Mixed fleets are normal.
  • Cache what repeats. Retrieval results, tool outputs, stable sub-answers, system-prompt prefixes.
  • Trim context per step. Each component gets what it needs, not the full conversation — cheaper, faster, and usually more accurate.
  • Stream and stage. Streaming output and early partial results cut perceived latency even when totals are unchanged; batch anything that can run offline.
Budget reality

Reflection and multi-agent patterns multiply calls by design. Reserve them for the steps where error analysis proved they earn their cost — not as a default garnish on every step.

Step 07

Pattern picker

Answer four questions about your task; get a starting architecture. It encodes the decision rules above — treat it as a first draft, then let evals overrule it.

1 · Can you write down the step sequence in advance?
2 · Does the task need external data or real actions (APIs, DBs, search, code)?
3 · Is output quality critical, and is the output checkable (runnable, testable, verifiable)?
4 · Do subtasks need different roles/tools, or run well in parallel?
